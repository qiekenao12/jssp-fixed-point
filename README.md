# Do Fixed-Point Predictions Improve Heuristic Action Selection? — Reproducibility Repository

Reproducibility package for the manuscript submitted to *Swarm and Evolutionary Computation* (SWEVO):

> **Do Fixed-Point Predictions Improve Heuristic Action Selection? Decision Sufficiency and Two-Solver Evidence from Job Shop Scheduling.**

The study asks whether empirical fixed-point (FP) predictions of search dynamics improve
*heuristic action selection* in job shop scheduling (JSSP). It separates **prediction quality**
(Hurdle I: do action-conditioned affine maps predict state transitions better than identity/pooled
baselines?) from **decision utility** (Hurdle II: do FP-derived decision features improve selected
action returns over strong NoFP controls on detached, independently repeated branches?), across
**two independent solver implementations** and a **prospective standard-benchmark extension**.
All models, seeds, splits and comparisons were locked locally before final/test collection;
every raw branch, frozen model, lock manifest and verification receipt is archived here.

**Headline findings (bounded, offline):** action-conditioned transition maps beat identity/pooled
baselines in the structurally informed critical-block stack (and in the 50-instance extension), yet
**no FP decision arm beats the strong NoFP controls or the best fixed static action** in either
reward regime; the apparent raw-reward action dominance reverses under cost normalization; the
noisy sample winner fails on fresh repeats under raw reward. No online FP-agent performance,
equivalence, or SOTA claim is made. See the manuscript and `RELEASE_NOTES.md` for scope boundaries.

Branches are *provenance counts*, not independent statistical units. The primary effect unit is the
**instance** (20 new synthetic final instances; 30 held-out standard benchmarks in the extension),
with exact signed-rank/Wilcoxon tests, Holm correction and instance-cluster bootstrap CIs.
The 32 synthetic instances are generated by a seeded uniform JSSP generator
(`scripts/prepare_fp_decision_study.py`): sizes 6×6, 10×5, 10×10, 15×10; 2 development + 1 validation
+ 5 final per size; independent uniform machine permutations per job; durations Uniform{1,…,99}.
The extension uses 50 classical benchmarks (Taillard `ta01–ta30`, Lawrence `la21–la40`), split
20 dev / 30 test with seed 2026112000, stratified by family×size; all 50 are new to the
critical-block stack (overlap with the historical *genetic* study is disclosed per instance in
`experiments/ext_standard_jssp/outputs/manifest_lock.json` → `overlap_disclosure`).

## 5. One-command independent verification

```bash
python scripts/verify_all.py
```

This runs, **from inside this repository**, using only numpy + stdlib:

1. **Lock integrity** — SHA256 re-verification of all 32 files in `final_lock.json` (primary) and
   all 10 new + 12 reused code hashes + 84 benchmark hashes in the extension `manifest_lock.json`,
   plus recomputation of `design_hash`, `instances_hash`, `lock_hash`, and the three documented
   post-lock engineering amendments (`code_amendment_001–003.json`).
2. **Primary synthetic cohort** — independent **synchronous-relaxation schedule audits** of all
   four raw grids (`tabu/development`, `tabu/validation`, `tabu/final`, `original/final`;
   87,600 branches, every saved schedule re-decoded independently of the solver), then the two
   **independent scalar replays**: `verify_fp_decision_statistics.py` (exact signed-rank/Holm from
   raw rewards + exported scores) and `verify_fp_decision_analysis_independent.py` (full score,
   choice, repeat and bootstrap-CI reconstruction from raw branches + frozen models).
3. **Prospective extension** — `verify_ext_schedules.py --split development|test` (stdlib-only
   synchronous time relaxation; 21,933 distinct schedules) and `verify_ext_replay.py`
   (72 paired contrasts, both targets, split-repeat diagnostics, per-size tables; max error ≤ 2.9e-16).
4. **Unit tests** — 15 solver-correctness / branch-isolation tests.
5. **Historical trigger cohort** — `analyze_trigger_comparison.py` re-audits all 800 paired runs
   (initialization fingerprints, 30,000-query budgets, VND sub-budgets, event gain accounting) and
   recomputes every statistic from the saved run JSONs; regenerated `summary.json`, CSVs and
   `report.md` must match the shipped receipts byte-for-byte.
6. **Repository hygiene** — max file < 50 MB, total < 300 MB, file count, forbidden-pattern scan.

Because the shipped receipts are **write-once** (each verifier refuses to overwrite an existing
audit), `verify_all.py` executes everything in a fresh temporary sandbox copy and compares each
regenerated report field-by-field against the shipped frozen receipt. Nothing in the repo is
modified. Expected final line:

```
TOTAL: 25 PASS / 0 FAIL        # 26 with --figures; 29 with --historical; 30 with both
```

Useful variants:

```bash
python scripts/verify_all.py --quick       # locks + hygiene only (seconds)
python scripts/verify_all.py --figures     # additionally regenerate all 8 figures in the sandbox
python scripts/verify_all.py --historical  # also audit the extracted historical raw archives (§6)
python scripts/verify_all.py --report verification_summary.json
```

One documented provenance exception is checked explicitly (not skipped): the frozen independent
review receipt records the hash of the *pre-revision* 2026-10-26 study document; the shipped
document is the revised version. The mismatch must equal exactly the documented revision pair,
and all six other reviewed hashes must match — see `RELEASE_NOTES.md` §5.

## 11. Important caveats

- All locks are **local timestamp + SHA256 freezes**, not externally witnessed preregistration.
- Receipts are write-once; verification runs in a sandbox (§5). Three engineering-only post-lock
  amendments are recorded with before/after hashes (`EXT/code_amendment_001–003.json`).
- Sanitization exceptions required by hash-lock integrity are documented in `RELEASE_NOTES.md` §4–5.
- Offline detached-branch outcomes are **not** online policy performance; synthetic gaps are
  relative to a workload lower bound, not known optima; failure to reject is not equivalence.
